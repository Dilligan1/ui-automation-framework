# Архитектура фреймворка

## Принцип

Тест не знает про Selenium. Он оперирует ролями и бизнес-действиями:

```python
self.user_page().login_page.login("user")
post_id = self.user_page().feed.publish_post(text)
```

Всё, что ниже — поиск элементов, ожидания, обработка перерисовки DOM — спрятано в слоях.

```
        тест (tests/)
            │  действие роли + assert
            ▼
   интерфейс роли (interfaces/)
            │  набор доступных страниц
            ▼
   страница (pages/<page>.py)
            │  локаторы + методы страницы
            ▼
   компонент (pages/**/components/, base_components/)
            │  переиспользуемый блок UI
            ▼
   BasePage → UIHelper → Waiter
            │  find/click/fill, ожидания по условию
            ▼
       Selenium WebDriver
```

## Слои

### `metaclasses/meta_locators.py`
Метакласс `MetaLocator` разбирает строковые атрибуты класса и превращает их в кортежи Selenium: строка с `//` становится XPath, строка с `.`, `#` или `[` — CSS-селектором. Благодаря этому локаторы в страницах читаются как данные, а не как вызовы API:

```python
_SUBMIT_BUTTON = "[data-testid='auth-login-btn']"   # не ("css selector", "...")
```

### `utils/waiter.py`
Все ожидания по условию: видимость, кликабельность, количество элементов, текст, атрибут. Отдельный метод `wait_for_spa_idle` — для SPA: `document.readyState == "complete"` наступает задолго до того, как отрисованы данные, поэтому дополнительно ожидается исчезновение спиннера.

Правило: `time.sleep` в коде фреймворка и тестов отсутствует.

### `utils/ui_helper.py`
Единственное место, где вызывается WebDriver API. Здесь же две страховки, без которых React-приложение регулярно даёт ложные падения:

- **StaleElementReferenceException** — узел перерисован между поиском и кликом: элемент ищется заново;
- **ElementClickInterceptedException** — элемент перекрыт тостом или модалкой: клик выполняется через JS.

### `base/base_page.py`
Общий предок страниц. Держит элементы каркаса приложения (логотип, навигация, кнопка выхода, тосты) и операции `open` / `is_opened` / `is_authorized`. Тосты вынесены сюда потому, что для многих действий всплывающее уведомление — единственный отклик интерфейса.

### `base_components/lists/base_list_handler.py`
Базовый обработчик коллекций: лента, список диалогов, уведомления, таблица пользователей в админке — всё это контейнер + однотипные строки.

Ключевые решения:
- строка ищется **по id или по тексту**, а не по позиции: список пересортировывается после каждого действия, а индексы разъезжаются;
- поля строки читаются **по имени** через карту `_FIELDS`, а не по номеру ячейки: добавление элемента в карточку не ломает тесты;
- `dump_rows()` прикладывает содержимое списка в Allure — когда строка не найдена, из отчёта сразу видно, что в списке было на самом деле.

### `interfaces/`
Наборы страниц по ролям. Отдельный интерфейс для модератора существует именно затем, чтобы ограничение прав было видно в коде: у модератора нет страницы управления пользователями.

### `pages/`
Страница объявляет свой `_PAGE_URL`, свои локаторы и методы уровня страницы. Сложные блоки выносятся в `components/` — форма публикации, карточка поста, блок комментариев, списки. Компонент можно переиспользовать: `PostCard` работает одинаково в ленте, в профиле, в закладках и на странице поста, потому что все его действия параметризованы id поста.

### `pages/flows/`
Многошаговые сценарии между страницами. Страница знает про свои элементы, флоу — про последовательность действий, поэтому «опубликовать пост и прокомментировать его» не дублируется в каждом тесте.

### `utils/storage_manager.py`
Приложение хранит JWT в `localStorage`, поэтому логин не нужно прогонять через форму в каждом тесте: первый тест логинится, токены сохраняются в файл, остальные подставляют их в браузер. Файл сессии один на роль и общий для всех xdist-worker'ов, а доступ к нему сериализуется `FileLock` — за прогон происходит ровно один вход на роль. Это не только экономия времени: на стенде есть дефект, при котором два одновременных входа одного пользователя дают 500 (см. [known-issues.md](known-issues.md)). При протухшей сессии выполняется обычный вход через форму, так что путь входа остаётся покрытым.

## Параллельный прогон

Два независимых уровня:

1. `runner.py` — `ProcessPoolExecutor` запускает наборы (smoke, regress) одновременно, каждый своим процессом pytest. Короткий smoke отдаёт результат, не дожидаясь регрессии.
2. `pytest-xdist` внутри набора — тесты распределяются по N браузерам.

Что делает это безопасным: драйвер создаётся на каждый тест, сессии разделены по worker'ам, тесты не зависят от порядка выполнения и убирают за собой созданные сущности.

## Правила, которые держат проект в форме

1. Тест наследуется от `BaseTest` и работает через интерфейс роли.
2. Никаких `time.sleep` и никаких прямых вызовов Selenium в тестах.
3. Никаких хардкодов данных: только `DataGenerator`.
4. Тест убирает за собой — стенд общий, `reset` из теста вызывать нельзя.
5. Локаторы — только внутри страниц и компонентов, никогда в тестах.
6. Ассерт пишется с сообщением, из которого видно ожидаемое и фактическое.
