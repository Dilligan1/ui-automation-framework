# Тест-план

## Уровни и их назначение

| Уровень | Маркер | Что проверяет | Когда гоняется |
|---|---|---|---|
| Smoke | `smoke` | Критичный функционал: вход, публикация, доступ к разделам | На каждый push |
| Regress | `regress` | Полное покрытие сценариев раздела, границы значений | Ночью и перед релизом |
| E2E | `e2e` | Сквозные сценарии, в том числе с двумя пользователями одновременно | Ночью и перед релизом |

Дополнительные маркеры: `critical` (бизнес-критичные проверки), `negative` (негативные сценарии), `slow` (дольше 10 секунд), `flaky` (карантин нестабильных).

## Приоритеты покрытия

| Приоритет | Функциональность | Обоснование |
|---|---|---|
| Blocker | Вход и выход из аккаунта | Без него недоступен весь остальной интерфейс |
| Blocker | Разграничение доступа к админ-панели | Дефект здесь — уязвимость, а не баг UX |
| Critical | Публикация, редактирование, удаление поста | Основной пользовательский сценарий |
| Critical | Реакции и комментарии | Массовые действия, высокая частота использования |
| Major | Загрузка изображения и её лимиты | Работа с файлами, типичная зона дефектов |
| Major | Управление пользователями в админке (роль, бан) | Последствия ошибки видны всем пользователям |
| Major | Приватный аккаунт: скрытие контента, запрос на подписку | Нетривиальная логика видимости |
| Minor | Поиск, тренды, смена языка | Отказ ухудшает UX, но не блокирует работу |

## Что проверяется на UI, а что нет

UI-тест проверяет **интерфейс**: отрисовку, доступность элементов, реакцию на действие, переходы между страницами. Логика бэкенда (коды ответов, валидация полей, права на уровне API) покрыта отдельным репозиторием [api-automation-framework] и здесь не дублируется.

Практическое следствие: подготовка данных для UI-теста, где это уместно, делается через API или БД, а не серией кликов. Проверка при этом остаётся на UI.

## Тестовые данные

Seed-набор песочницы фиксирован и восстанавливается `POST /api/reset`. Восемь пользователей покрывают состояния, которые иначе пришлось бы готовить вручную: верифицированный, с медиа-контентом, приватный, без постов, забаненный, модератор, администратор.

Всё, что тест создаёт сам, генерируется `DataGenerator` и удаляется в `finally`. Правило: **после прогона стенд должен остаться в том же состоянии**, в котором был до него.

## Устойчивость тестов

| Риск | Как снимается |
|---|---|
| Гонки при перерисовке React | Повтор поиска элемента в `UIHelper.click` |
| Тост перекрывает кнопку | Клик через JS при перехвате |
| Данные не успели отрисоваться | `wait_for_spa_idle`, ожидания по условию вместо `sleep` |
| Список пересортировался | Поиск строки по id или тексту, а не по позиции |
| Клик «проходит», но не срабатывает | `UIHelper.click_until` — проверяется результат клика (раскрылось меню, сменился адрес, изменился счётчик), а не факт клика |
| Модальные окна браузера поверх страницы | Отключены в опциях драйвера — см. ENV-001 в [known-issues.md](known-issues.md) |
| Флакующий тест портит прогон | `--reruns=1` только для инфраструктурных исключений (таймаут, stale, перехват клика) — логические падения не перезапускаются |

Перезапуск настроен намеренно узко: он не должен маскировать реальные дефекты приложения.

## Параллельный прогон

- Драйвер создаётся на каждый тест — состояние браузера не протекает между тестами.
- Сессия роли сохраняется в общий файл под `FileLock` — за прогон происходит один вход на роль, параллельные worker'ы переиспользуют его (и не ловят BUG-001 при одновременном входе).
- Тесты не зависят от порядка выполнения и не делят изменяемые сущности.
- `POST /api/reset` вызывается только мастер-процессом до старта worker'ов, никогда из теста.
